# AI Agent 内容写入设计

> 本文档写在实现之前，描述目标形态，不代表已落地。

## 背景

站长希望自己的 AI Agent 能直接往博客写文章，而不是「Agent 生成 → 人工复制 → 后台粘贴」。

调研中的关键发现：**Agent 其实已经连在这个博客上了**。Claude Code 会话中挂载的 MCP server `dh-search`，其 instructions 与 `aigateway/handler_mcp.go:90` 的 `mcpInitialize` 返回值完全一致 —— 说明 `/api/gateway/v1/mcp` 这条链路（API Key 鉴权 → JSON-RPC → 工具调用 → 计费/限流）已经在生产使用。

因此本设计**不新造接入通道**，而是给这个已经跑通的 MCP 端点增加内容写入工具，Agent 侧零配置。

### 已确定的决策

| 决策 | 结论 |
|---|---|
| 接入形态 | 只做 MCP 工具，不额外提供 REST |
| 发布策略 | 直接发布，不引入草稿态 |
| 身份标识 | 前台与后台都要标明「这是 AI Agent 发布的」 |
| 多 Agent | 从一开始就按多个 Agent 共用博客来设计 |
| 工具范围 | 创建、列表、读取、更新、上传配图 |
| 改站长的文章 | 默认禁止。需站长从后台生成有效期 1 小时的临时 Token |

两条设计重心：

1. **多 Agent** 意味着需要的是**作者身份**，而不是一个 `is_ai` 布尔值。
2. **临时 Token** 是本设计唯一的强闸门。既然选了直接发布、不走草稿审核，那么「Agent 能凭长期凭证改写站长的既有文章」就是风险最大的一条路径 —— 用短时、需站长主动发起的一次性授权把它关掉。

### 预期结果

- 站长在后台给某把网关 API Key 勾上「内容写入」权限并填写署名，那把 key 就成为一个具名 Agent
- Agent 可自由创建新文章、改自己写的文章、上传配图
- Agent 想改站长写的文章时会被拒绝，并被告知需要向站长索取临时 Token
- 文章在前台带署名徽标（如「AI · Claude」），后台列表有「作者」列
- 每次写入、每次临时授权的签发与使用，都在事件日志留痕

## 架构设计

### 一、抽出 MCP 协议层 `internal/platform/mcp/`

现状：JSON-RPC 骨架写死在 aigateway 内，`handler_mcp.go:109` 直接硬编码 `params.Name != mcpToolWebSearch` 就报错，无法容纳第二个工具。

抽出纯协议包（无业务逻辑，与 `platform/ai`、`platform/search` 同性质）：

- `jsonrpc.go` —— 从 `aigateway/mcp.go:43-148` 平移 `jsonRPCRequest/Response/Error`、`rpcResult`、`rpcFailure`、`isNotification`、`mcpText`、`mcpToolError`
- `server.go` —— 工具注册表与分发

```go
// Tool 是挂到 MCP 端点上的一个工具。
type Tool interface {
    // Definition 接收 ctx 是因为工具描述可能依赖调用者身份：
    // web_search 的 provider 枚举就取决于当前 key 能用哪些供应商。
    Definition(ctx context.Context) Definition
    Call(ctx context.Context, args json.RawMessage) Result
}

type Server struct { name, version, instructions string; tools []Tool }
func (s *Server) Register(tools ...Tool)
func (s *Server) Handle(ctx context.Context, body []byte) (response any, isNotification bool)
```

`Handle` 承接 initialize / ping / tools/list / tools/call 与版本协商（`negotiateProtocolVersion`）。aigateway 的 handler 退化成「读 body → 交给 Server → 写响应」。

**保持不变**：端点路径 `/api/gateway/v1/mcp`、鉴权中间件、限流、配额、计费。Agent 侧 MCP 配置不用改。

**需要调整**：`mcpServerName` 从 `dh-blog-search-gateway` 改为 `dh-blog`，version 提到 `2.0.0`，instructions 重写为同时涵盖搜索与写作（`serverInfo.name` 只用于展示，客户端按自己配置里的名字挂载，不影响已有配置）。

### 二、新增模块 `internal/modules/agentapi/`

Agent 面向的能力需要同时用到 article、文件上传，还要自己管理临时授权。按项目约定（不跨模块 import 对方 repository/service，依赖由使用方定义窄接口、在 registry 接线），单独立一个模块承载：

```
agentapi/
  module.go      窄接口定义 + 装配 + 路由注册
  model.go       EditGrant（临时授权）
  repository.go  授权的存取
  service.go     授权签发/校验/吊销
  handler.go     后台签发与管理接口
  tools.go       5 个 MCP 工具
  *_test.go
```

```go
// agentapi/module.go —— 使用方定义的窄接口
type Articles interface {
    List(ctx context.Context, keyword string, page, pageSize int) ([]ArticleBrief, int64, error)
    Get(ctx context.Context, id int) (*ArticleDetail, error)
    Create(ctx context.Context, input CreateInput) (int, error)
    Update(ctx context.Context, input UpdateInput) error
}
type Images interface {
    SaveBlogImage(ctx context.Context, fileName string, data []byte) (url string, err error)
}
```

对外提供 `MCPTools() []mcp.Tool`，并在 AdminAPI 上注册临时授权的管理路由。

### 三、依赖装配

aigateway 是端点持有者，由它定义窄接口收纳外部工具：

```go
// aigateway/module.go
type ToolSource interface{ MCPTools() []mcp.Tool }
type Dependencies struct { /* ...既有字段... */ ExtraTools ToolSource }
```

`registry.go` 接线（`buildContext` 惰性记忆化，路由顺序无需等于依赖顺序）：

```
agentapi  ← article.ContentService() + files/admin 的图片写入 + eventlog
aigateway ← agentapi.MCPTools()
```

依赖方向 `aigateway → agentapi → article/files`，无环。`moduleRegistrations` 追加 `agentapi` 一项（`MigrationModels` 返回 `EditGrant`），**`registry_test.go` 硬编码了模块名与顺序，需同步更新**。

article 模块在 `module.go` 暴露 `func (m *Module) ContentService() ContentService`，把现有 `articleRepository` 的能力以接口形式对外，不泄露 repository 本身。

## 数据模型变更

### `articles` 表 —— 作者身份

```go
// article/model.go
// AuthorType 为空表示站长本人（历史文章天然如此），"agent" 表示 AI 写入。
AuthorType  string `gorm:"column:author_type;index" json:"authorType"`
// AuthorName 是署名快照。存快照而非只存 key id：key 改名或删除后署名仍在，
// 且列表查询不必 join。
AuthorName  string `gorm:"column:author_name" json:"authorName"`
// AuthorKeyID 溯源到具体凭证，也是「谁能免授权改这篇」的判据。
// json:"-" 是因为公开接口不该泄露内部 key id。
AuthorKeyID int    `gorm:"column:author_key_id;index" json:"-"`
```

AutoMigrate 加列即可。存量文章三个字段为零值 —— 前台不显示徽标（与现状一致），且天然落入「站长撰写、改动需授权」这一侧，这正是想要的默认。

### `ai_gateway_api_keys` 表 —— 能力与署名

```go
// aigateway/model.go
// Scopes 是逗号分隔的能力清单。空值表示仅 search —— 与 AllowedProviders
// 的「空 = 全部」相反，这是刻意的：否则升级后所有存量 key 会凭空获得写权限。
Scopes     string `gorm:"column:scopes" json:"scopes"`
// AuthorName 是这把 key 写文章时的署名，留空则回退到 Name。
AuthorName string `gorm:"column:author_name" json:"authorName"`
```

| scope | 含义 |
|---|---|
| `search` | 联网搜索（默认，空值等价于此） |
| `content:read` | 列表与读取文章 |
| `content:write` | 创建文章、更新**本 key 自己创建的**文章、上传配图 |

注意这里**没有**「可以改任何文章」的长期 scope —— 那个能力只能由临时 Token 临时给予。

`tools/list` 按 scope 过滤：没有写权限的 key 根本看不到写作工具，模型不会浪费 token 尝试。

### 新表 `agent_edit_grants` —— 临时编辑授权

```go
// agentapi/model.go
// EditGrant 是站长临时授予 AI Agent 修改既有文章的凭证。
//
// 它存在的原因是本系统选择了「Agent 写入即发布」，没有草稿审核这道闸。
// 于是改写站长既有文章成了风险最高的动作：模型误判、或联网搜索时读到的
// 网页里带了注入指令，都可能悄悄改掉已发布的内容。把这个能力从长期凭证
// 里摘出来，改成站长主动发起、一小时后自动失效的短时授权。
type EditGrant struct {
    model.BaseModel
    TokenPrefix string     // 公开部分，后台列表与吊销用
    TokenHash   string     // 校验走常数时间比对
    TokenPlain  string     // 只由后台的 reveal 动作读取，便于站长再复制一次
    ExpireAt    time.Time  // 签发时间 + 1 小时
    ArticleID   int        // 0 = 不限篇；预留按篇绑定
    Revoked     bool
    UsedCount   int
    LastUsedAt  *time.Time
    Note        string     // 站长自己的备注，如「让 Claude 改错别字」
}
```

设计取舍：

- **存 DB 而非内存缓存**：进程重启后授权仍有效，且后台能列出当前有效的授权并随时吊销，可审计。
- **1 小时内可多次使用**，不做一次性消耗 —— 站长的意图通常是「这一小时里你帮我改」，逐次重新签发太琐碎。`UsedCount` 记录使用次数供事后核对。
- **存 hash + 明文**：照 `APIKey.KeyPlain`（`aigateway/model.go:159`）的先例，校验走 hash，明文只在后台显式 reveal 时读取。生命周期只有 1 小时，风险可控。
- **`ArticleID` 预留但第一版不在 UI 暴露**：默认签发不限篇的授权。若日后想收紧到「只授权改这一篇」，字段和校验逻辑已就位。

过期的授权由一个轻量清理逻辑在签发时顺带删除（无需独立定时器）。

## 授权规则

`update_article` 的判定顺序：

1. key 没有 `content:write` → 拒绝（且该工具根本不会出现在 `tools/list` 里）
2. 目标文章的 `author_key_id` == 当前 key → **放行**，无需 Token
3. 否则（站长写的，或别的 Agent 写的）：
   - 未传 `edit_token` → 拒绝，错误文本明确告知需要向站长索取
   - Token 无效 / 已过期 / 已吊销 / 绑定了别的文章 → 拒绝，分别给出可区分的原因
   - Token 有效 → 放行，`UsedCount++`，写事件日志

第 3 条把「站长写的」和「别的 Agent 写的」一视同仁，规则更简单也更安全：**任何 key 都只能免授权地改自己写的东西**。

错误文本要写得让模型能自己纠正，例如：

> 这篇文章不是本 Agent 创建的，修改需要临时授权 Token。请让站长在后台「文章管理 → 生成 AI 修改授权」签发一个（有效期 1 小时），并把它作为 edit_token 参数传入。

### 后台管理接口（AdminAPI，JWT 鉴权）

```
POST   /api/admin/agent/grants              签发（可选 note、articleId），返回明文 Token
GET    /api/admin/agent/grants              列出未过期的授权及使用情况
GET    /api/admin/agent/grants/:id/reveal   再看一次明文
DELETE /api/admin/agent/grants/:id          立即吊销
```

## 工具契约

工具名不加前缀（MCP 客户端会自动按 server 名加命名空间）。

### `list_articles`
参数：`keyword?`、`page?`(默认 1)、`page_size?`(默认 20，上限 50)

返回：id、标题、分类、标签、摘要、字数、创建时间、作者，**以及 `editable` 布尔值** —— 标明这篇本 key 能否免授权修改。让 Agent 提前知道哪些文章需要向站长要 Token，而不是撞了墙才知道。

### `get_article`
参数：`id`

返回：全文 Markdown 及元信息，同样带 `editable`。加密文章（`is_locked`）不返回正文。

### `create_article`
参数：`title`(必填)、`content`(必填，Markdown)、`summary?`、`category?`(分类名，不存在则报错并列出可用分类)、`tags?`(名称数组)、`thumbnail_url?`

复用 `ArticleRepository.SaveArticle`（`article_repository.go:71`），因此自动继承：字数统计、标签解析、分类默认标签、缓存清理。未传 `summary` 时仍走后台任务自动生成摘要与标签（`handler_articles.go:64-70`）。写入时填上 `author_type='agent'`、`author_name`、`author_key_id`。

**重复保护**：同标题文章已存在时不静默重复创建，返回错误并提示改用 `update_article`。

### `update_article`
参数：`id`(必填)、`edit_token?` + `title?`/`content?`/`summary?`/`category?`/`tags?`

仅传的字段被更新。复用 `UpdateArticle`（`article_repository.go:92`），它已处理「summary 为空时保留库里已生成的摘要」。授权规则见上一节。

`edit_token` 在工具描述里要明确写：**只有改非本 Agent 创建的文章时才需要，由站长从后台签发，有效期 1 小时**。

### `upload_image`
参数：`file_name`(必填)、`data`(必填，base64)

返回：可直接写进 Markdown 的 URL。

落地复用 admin 模块的既有链路（`admin/handler.go:24`）：存进 `GetProtectedDirectoryID(ctx, "博客")` 拿到的固定目录，文件名前缀时间戳去重。文件经 `/api/博客/*filepath` 静态路由（`files/module.go:99`）公开，返回 `/api/博客/<时间戳>_<文件名>`，与后台编辑器上传的 URL 形态一致；记录属主为管理员用户（id=1），后台 Files 界面可预览与管理。

限制：解码后 ≤ 5MB；MIME 必须是 image/*；只接受 base64，不接受 `source_url`（避免 SSRF）。

### 请求体上限

`maxMCPRequestBody` 现为 64KB（`aigateway/mcp.go:25`），一篇长文的 Markdown 就可能超，base64 图片必然超。提到 **8MB**。搜索请求本来就小不受影响；恶意大 body 由 API Key 鉴权与限流兜底。除 8MB 上限外，内容工具同样受每把 Key 的 `RateLimitPerMin` 每分钟限制，且与搜索共享同一个额度池（`mcpToolsFor` 用限流包装器包住每个附加工具），查询与写入共用一个预算，防止被窃取的写 Key 全速刷创建与上传。

## 审计

eventlog 已有 `SourceArticle` 常量（`eventlog/model.go:23`）。照 `adapters.go` 的 Reporter 模式加 `ContentReporter`，在以下时机 `Publish`：

| 时机 | Kind | Status | Title 示例 |
|---|---|---|---|
| Agent 创建文章 | `agent_write` | success | `Claude 发布了《...》` |
| Agent 改自己的文章 | `agent_write` | success | `Claude 修改了《...》` |
| 站长签发临时授权 | `edit_grant` | running | `已签发 AI 修改授权，1 小时后失效` |
| Agent 持 Token 改文章 | `agent_write` | success | `Claude 持临时授权修改了《...》` |
| 无 Token / Token 失效被拒 | `agent_write` | failed | `Claude 尝试修改《...》被拒绝` |

最后一条尤其重要：它是发现「Agent 在试图改不该改的东西」的唯一信号。

```bash
# 1. 后台给一把 key 勾上 content:write 并填署名
# 2. 确认工具已出现
curl -s localhost:2233/api/gateway/v1/mcp -H "X-API-Key: $KEY" \

# 3. 写一篇
curl -s localhost:2233/api/gateway/v1/mcp -H "X-API-Key: $KEY" -d '{"jsonrpc":"2.0","id":2,
  "method":"tools/call","params":{"name":"create_article",
  "arguments":{"title":"测试","content":"# 正文","category":"默认分类"}}}'
# 4. 改自己刚写的那篇 —— 应直接成功，不需要 Token
# 5. 改一篇站长写的老文章（不带 edit_token）—— 应被拒绝，错误文本提示索取授权
# 6. 后台签发授权，带上 edit_token 重试第 5 步 —— 应成功

# 9. 用一把只有 search 的旧 key 重复第 2 步，应看不到任何写作工具
```

第 5、7、9 步是权限回归的关键：存量 key 不得因升级获得写权限，站长的文章不得在无授权或授权失效时被改动。

Token 过期的验证不便手工等待 1 小时，改在单测里注入时钟覆盖（service 持有 `now func() time.Time`，与 `aigateway/auth.go:54` 的 `s.now()` 同风格）。

## 实现注记（相对本文的最初形态）

定稿时与最初形态一致，但以下细节在实现中确认并固化，供后续维护对照：

- **`AuthorName` 字段更名 `Byline`**：`ai_gateway_api_keys` 上计划承载署名快照的字段先叫 `AuthorName`，与 `agentapi.Identity.AuthorName()` 方法同名，装配时容易混淆。实现中改名为 `Byline`（DB 列 `author_name`、JSON 字段 `authorName` 均不变，向前端与签名行为无影响）。
- **MCP 服务器按请求构造**：为支持按 key 过滤 `tools/list` 与 `tools/call`，协议服务器（`mcp.Server`）不再在模块启动时构建一次，而是每次请求在 `handler.MCP` 里按当前 API Key 组装工具表后 `Handle`。代价是每请求几个小结构体，换来「没有 scope 的 key 连工具名都看不到」。
- **`tools/list` 语义校验失败的呈现**：参数解析与语义校验的失败最初按 JSON-RPC 错误处理；实现中除「未知工具/未知方法」等协议层错误外，一律降级为工具结果内的 `isError: true`（`mcp.ToolError`），让模型直接读到原因并自行纠正，而不是被客户端当成传输错误吞掉。
- **search 恒为基线能力**：`search` scope 始终可空等语义成立（后端 `NormalizeScopes` 仍接受它），但实现确认联网搜索对任何 Key 无条件可用，后台 Key 表单不再把 `search` 作为可勾选项——能力多选只配置 `content:read` / `content:write`。

## 风险与后续

- **prompt injection**：Agent 会联网搜索，网页内容可能携带注入指令。缓解手段是三层：新建文章不影响既有内容；改既有内容需站长主动签发的短时 Token；所有动作（含被拒绝的尝试）进事件日志。
- **Token 泄露**：站长会把明文 Token 贴进 Agent 对话，可能被记录在对话历史里。1 小时有效期 + 可随时吊销是主要约束；`ArticleID` 字段已预留，若要进一步收紧可改为按篇签发。
- **多 Agent 隔离**：第一版规则已天然隔离 —— 任何 key 只能免授权改自己写的文章，Agent 之间互改同样需要 Token。
- **后续可加**：评论管理工具、网盘操作工具 —— 协议层与 agentapi 模块都已为此留好扩展位。
